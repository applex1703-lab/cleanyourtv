# Проверенный эталон поведения лаунчера

Состояние подтверждено пользователем 23 октября 2026 года: «Идеально».
Рабочий коммит: **`6598d87`** (получать полную версию через `git rev-parse 6598d87`).
Этот документ фиксирует результат проверки на ТВ, а не обещание одинаковых пикселей на любом экране.

## Что сохранять

- Основной установленный v1: `com.gathin.tvhome`. Не удалять и не изменять при тестировании v2.
- Редактируемый форк: `com.gathin.tvhome.v2`.
- Верхний ряд слева направо: **Wi-Fi → системные Настройки → ползунки настроек лаунчера**.
- Sources на главном экране скрыт; системный Input/HDMI не отключать.
- В панели настроек один экран с четырьмя функциями:
  1. Приложения в ряду.
  2. Непрозрачность панели дока.
  3. Обои.
  4. Изменить порядок приложений.
- Цветной ambient-фон показывается при фокусе на dock. При фокусе во втором и следующих рядах
  цвет приложения не окрашивает фон. Не отключать ambient глобально: это убирает его и у dock.
- При вертикальной навигации ряды плавно движутся под рамкой с фиксированной экранной высотой.
  При горизонтальной навигации сохраняются анимации выделения и перемещения рамки.
- APK содержит русский и английский; остальные переводы остаются в исходниках.

## Измеренный эталон: четыре колонки

ТВ: TCL G07, Android 11, экран 1920×1080, плотность 2 px/dp.
Измерения относятся к штатной конфигурации проверенного запуска с четырьмя колонками;
другие плотности, количество колонок, тема и настройки могут менять геометрию.

| Границы RecyclerView | `[112,233]…[1808,1080]` | такие же |
| Шаг колонок | 424 px | 424 px |

На v2 проверено **Down → Down → Up → Up**: Y плитки и рамки остаются одинаковыми

## Причины прошлых расхождений — не повторять

1. **Папка `cleanyourtv-main` и установленный v1 не являются одним и тем же эталоном.**
   Совпадение исходников с этой папкой не доказывает совпадение с картинкой установленного v1.
2. Боковые padding RecyclerView по 10 dp сужали шаг колонок с 424 до 414 px.
   В проверенной версии `paddingStart` и `paddingEnd` сетки равны 0 dp;
   внешние отступы всего Home сохранены.
3. Расчёт плитки уменьшал ширину с 180 до 177 dp даже при четырёх колонках.
   В `AppAdapter.tileWidthPx()` сохранён размер 180 dp, когда ячейка достаточно широка.
   Не увеличивать плитки безусловно при большем числе колонок или узком экране.
4. Привязка к началу списка и decoration inset давали вертикальную разницу 12 px.
   Проверенный dock baseline учитывает добавочные 6 dp в layout padding и 6 dp decoration inset.
5. Мгновенный `scrollBy()` убирал вертикальную анимацию. В обычном режиме используется
   `smoothScrollBy()`, мгновенная прокрутка оставлена для отключённых анимаций/reduced motion.
6. `onScrolled` не должен утягивать экранную рамку вслед за рядами в обычном dock-layout.
   Редактор порядка обрабатывается отдельно.
7. Измерять позицию рамки нужно с учётом конечного смещения ряда; не запускать её Y-анимацию дважды.
8. Файл Outfit у v1 и v2 одинаковый, но способ задания веса отличался.
   Для основных надписей Home используются явные оси `fontVariationSettings` как в v1.
   Соответствующий стиль ограничен `values-v28`; `minSdk` остаётся 26.
9. Визуальный порядок верхних кнопок и порядок D-pad должны совпадать.
   Не поддерживать отдельный противоречащий XML список соседей.

## Цвет фона: почему HEX на экране выглядит иначе

Проверено 24 октября 2026 года по двум PNG-скриншотам с одного ТВ, при фокусе на YouTube в dock.
Это ожидаемое затемнение исходной ambient-маской, а не установленный факт искажения телевизором.
HEX в палитре — **цвет тонировки**, не обещание такого же RGB у итогового фона.

### Оригинальная структура свечения

- Обычный режим `radial`: маска 480×270, растягиваемая на экран.
- Центр: `32%` ширины, `42%` высоты; радиус: `62%` ширины.
- Альфа в точках градиента: `0x5C → 0x26 → 0x00`, позиции: `0 → 0.45 → 1`.
  Максимальная непрозрачность около **36%**, затем около **15%**, затем нулевая.
- Белая маска тонируется через `BitmapDrawable.setTint()` (SRC_IN), сохраняя её альфу.
- На чёрном фоне итоговый канал приблизительно равен `round(канал HEX × альфа / 255)`.
  Дополнительная прозрачность View и фон под маской также влияют на результат.
- Эта формула и значения относятся к обычному radial-режиму после завершения перехода.
  У theme-вариантов `cinematic` и `horizon` другая маска: не применять к ним эти числа автоматически.

### Измерения, а не подбор вслепую

| Точка на скриншоте 1920×1080 | Чистый красный `#FF0000` | Наш прежний `#B82018` |
| --- | --- | --- |
| Центр `(614,453)` | `#5C0000` (92,0,0) | `#420C09` (66,12,9) |
| `(422,453)` | `#490000` | `#350907` |
| `(806,453)` | `#490000` | `#350907` |
| `(230,345)` | `#340000` | `#260705` |
| `(1536,432)` | `#0F0000` | `#0B0201` |

Дополнительно для прежнего `#8B1826` в центре было измерено **`#32090E` (50,9,14)** —
ровно ожидаемое смешивание с чёрным при альфе 92/255. У этого исходного HEX синего больше,
чем зелёного (38 против 24), то есть холодный бордово-розовый оттенок уже присутствует в самом цвете.

Разница между двумя красными уже есть в файлах скриншотов, до физического экрана ТВ.
Влияние настроек изображения/панели ТВ этим не исключено, но обвинять их без отдельной проверки нельзя.

### Принятое решение

- Пользователь выбрал красный **как на первом снимке**: исходная тонировка **`#FF0000`**.
- Это закреплено коммитом **`667861f`**, установленным на ТВ; пункт называется «Красный».
- Не пытаться получить чистый красный добавлением зелёного/синего или тёмным бордовым HEX:
  это меняет оттенок и дополнительно уменьшает яркость.
- Не «компенсировать» тусклость заменой оригинальной маски, её центра, радиуса или альфы.
  Не возвращать диагональные двухцветные заливки: пользователь явно выбрал оригинальную структуру.
- Цвета проверять на фактическом фоне лаунчера, а не только как сплошную заливку в редакторе.
  Сначала снять PNG и сравнить пиксели свободной области после завершения анимации;
  затем оценить экран пультом/глазами в одинаковом режиме изображения.
- Если в PNG RGB соответствует расчёту, но на панели заметно иначе, только тогда отдельно
  исследовать настройки изображения ТВ. Не менять их автоматически.
- Снимки сравнения сохранены локально в одобренной временной папке `opencode/red-comparison`:
  `01-current-red.png` и `02-our-red.png`. Это временные файлы, не гарантированное постоянное хранилище;
  численные результаты выше сохраняют доказательство. Скриншоты в Git не добавлять.

## Проверка после изменений

- Сначала четыре колонки и одинаковые условия v1/v2. Измерять обычную плитку отдельно от выделенной.
- Сравнить шаг колонок, размеры плитки/рамки и Y после завершения анимации.
- Проверить Left/Right по верхнему ряду без пропуска ползунков; затем все края сетки.
- Проверить Down → Down → Up → Up, быстрые повторные нажатия и возврат на dock.
- Проверить цветной фон на dock и его исчезновение ниже dock.
- Проверить четыре настройки на одном экране и возврат после reorder.
- Проверить 5–7 колонок отдельно: пиксели из таблицы к ним не применять.
- Запустить Python-регрессии `tests.test_launcher_panel_contract`, `tests.test_resource_duplicates`,
  `tests.test_hebrew_resources`, затем полный CI: JVM tests, lint, release build и APK size gate.
- Зелёный CI не заменяет визуальную проверку на ТВ и реальном пульте.

## Если появилась регрессия

- Сначала сравнить изменение с `6598d87`, например:
  `git diff 6598d87 -- launcher/`.
- Не сбрасывать весь репозиторий и не затирать последующую работу. Откатывать только
  подтверждённое изменение отдельным коммитом после просмотра diff.
- Не переименовывать пакет снова и не удалять v1 ради обновления.
- Постоянный ключ подписи для CI пока **не настроен**. Текущий debug-ключ создаётся runner-ом;
  следующий APK может не установиться поверх v2. Переустановка стирает настройки v2 и требует
  явного согласия пользователя. Для нормальных обновлений нужен постоянный ключ, хранящийся
  приватно, не в Git. Не обходить проверку подписи Android.
